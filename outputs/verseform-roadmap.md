# Verseform — Tight Roadmap

## Delivery rule

This roadmap is intentionally short. Each item is an end-to-end user outcome with its contract, implementation, failure behavior, and proof included. Do not create separate foundation milestones or one item per toolbar button. A newly discovered defect stays inside the active item unless it is independently shippable or changes product scope.

### First independent-user session

Use invented writing and an approximately 20–30 minute observed session. Give the tester the ordinary release page and quick-start material; record any coaching instead of counting coached completion as independent discovery.

1. Download and install the exact candidate, identify its version, and start writing. Record Windows version, WebView2 version, actual display/text scale, and any unsigned-installer friction.
2. Format a short document; discover delimiter-triggered detection; preview and insert a verse/range; undo; inspect an invalid reference; select a translation and explain which translation was inserted.
3. Save to a chosen location, reopen, understand autosave versus recovery, and restore a prepared recovery without losing a second draft. Exercise one cancellation and one failed destination with disposable data.
4. Start offline with WEB, then reopen online with the saved preferred translation. Compare the dedicated PDF review with a multi-page export and use an available printer or record that physical printing remains unverified.
5. Locate version/help/credits and the feedback route. Record task completion, hesitation, coaching, recoverability, and the tester's willingness to use it again; collect no private document, cache, or recovery files. The owner may transcribe optional feedback for a tester without GitHub access.

Do not close this item using automated journeys in place of a person. The first-user gate is complete when there are no unresolved writing-loss, scripture-correctness, or core-task blockers; fix observed blockers with the cheapest regression and retest the affected task. Use subsequent users to decide broader usability work.

## Scope gates

- `VFM-010` is the only bootstrap gate. If the central interaction or output route is wrong, change it before broad formatting work.
- The DBS gate was resolved in `VFM-040` by the public ARC JSON contract and owner-confirmed cache permission (`D-013`–`D-015`).
- `VFM-090` is behavior-preserving. Do not mix visual redesign, document-format change, provider change, or new user capability into the kernel migration.
- `VFM-100` consumes the kernel's command/view-model contracts. Do not begin it by adding another UI-local control path.
- No second operating system, cloud feature, DOCX work, or editable page-layout feature enters this roadmap without an explicit product decision.
- The owner approved `VFM-180` on 2026-09-07 after the 0.2.3 release. Its browser, persistence, output, and provider contract is recorded in the requirements. The Windows independent-user session remains open and must not be counted as completed by browser implementation.
- Alpha feedback may reorder queued items, but it must not weaken document safety, citation correctness, attribution, or privacy.

## Completed Alpha baseline

A Windows user can install Verseform, write and format a document, detect valid/fuzzy/invalid references, preview and insert authorized scripture with one click, work offline with clearly identified WEB text, recover and reopen local work, and print or export an attributed PDF without creating an account.

## Definition of Beta

A daily Windows user receives the complete Alpha behavior through a compact, coherent interface whose visible state cannot disagree with application state; common commands behave identically from menus and shortcuts; documents survive Alpha upgrade, recovery, autosave, and late asynchronous results; DBS and license credits are locally inspectable; and the tested installer, privacy, attribution, accessibility, performance, and known-limit claims are accurate and reproducible.
